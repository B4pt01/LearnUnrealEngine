Architecture du moteur

Avant d'écrire la moindre ligne de gameplay, il faut comprendre comment Unreal organise un jeu : qui possède quoi, qui décide des règles, qui contrôle le personnage. Ce chapitre est probablement le plus important du site : tout le reste s'appuie dessus.

Dans ce chapitre

  • Comprendre la hiérarchie UObject → AActor → APawn → ACharacter
  • Construire des objets par composition avec les Components
  • Maîtriser le Gameplay Framework : GameMode, GameState, PlayerController, PlayerState, Pawn, HUD, GameInstance
  • Savoir où ranger chaque donnée de votre jeu
  • Découvrir les Subsystems, le World et les Levels

Vue d'ensemble

Quand vous lancez votre jeu, Unreal crée une série d'objets imbriqués. Le moteur (UEngine) crée une GameInstance qui vit pendant toute la session. Celle-ci charge un World (le monde de jeu), qui contient un ou plusieurs Levels (niveaux), qui eux-mêmes contiennent des Actors (tout ce qui est placé dans le monde). Enfin, chaque Actor est composé de Components.

Gardez ce schéma en tête : quand une donnée doit survivre à un changement de niveau, elle ne peut pas vivre dans un Actor (qui est détruit avec son niveau). Elle doit remonter plus haut, dans la GameInstance par exemple.

UObject : la brique de base

Presque tout ce que vous manipulerez dans Unreal hérite de UObject. C'est la classe racine du système d'objets du moteur. Le simple fait d'hériter de UObject donne gratuitement plusieurs super-pouvoirs :

Réflexion
Le moteur « connaît » vos classes, leurs variables et leurs fonctions. C'est ce qui permet de les voir dans l'éditeur et de les utiliser en Blueprint.
Garbage Collection
La mémoire est libérée automatiquement quand plus personne ne référence l'objet. Pas de delete manuel.
Sérialisation
Les objets peuvent être sauvegardés sur disque (assets, niveaux) et rechargés.
Valeurs par défaut (CDO)
Chaque classe possède un objet modèle, le Class Default Object, qui contient ses valeurs par défaut.
Réplication
Les propriétés peuvent être synchronisées automatiquement en réseau.

Actors : tout ce qui vit dans le monde

Un Actor est n'importe quel objet qui peut être placé ou créé (spawné) dans un niveau : un mur, une lumière, une caméra, un ennemi, une pièce à ramasser, une zone de déclenchement invisible… Si ça existe dans le monde, c'est un Actor.

Point important : un Actor seul ne sait presque rien faire. Il n'a même pas de position à lui ! Sa position, sa rotation et son échelle (sa transform) sont celles de son Root Component, le composant racine. Ce sont les Components qui donnent à l'Actor son apparence et ses capacités.

Piège classique

Un Actor créé sans aucun composant n'a pas de transform : GetActorLocation() renverra toujours (0, 0, 0) et vous ne pourrez pas le déplacer. Donnez toujours un RootComponent à vos Actors (au minimum un USceneComponent).

Le cycle de vie en bref

Chaque Actor passe par des étapes bien définies. Les deux que vous utiliserez tout le temps sont BeginPlay (le jeu commence pour cet Actor) et Tick (appelé à chaque frame). Le cycle complet est détaillé dans le chapitre C++ avancé.

Components : la composition avant l'héritage

Plutôt que de créer une classe énorme qui sait tout faire, Unreal encourage la composition : on assemble un Actor à partir de petites briques indépendantes. Une torche murale, par exemple, n'est rien d'autre qu'un Actor qui contient :

  • un UStaticMeshComponent pour le modèle 3D du support ;
  • un UPointLightComponent pour la lumière ;
  • un UNiagaraComponent pour les flammes ;
  • un UAudioComponent pour le crépitement du feu.

Les trois familles de composants

UActorComponent

Comportement pur

Pas de position dans le monde. Idéal pour de la logique réutilisable : système de santé, inventaire, gestion des munitions.

USceneComponent

Possède une transform

A une position et peut être attaché à d'autres composants. Exemples : caméra, Spring Arm, point d'apparition de projectile.

UPrimitiveComponent

Visible ou collisionnable

Peut être rendu à l'écran et/ou générer des collisions. Exemples : Static Mesh, Skeletal Mesh, Box, Sphere, Capsule.

La hiérarchie d'attachement

Les Scene Components forment un arbre : chaque composant est attaché à un parent et suit ses mouvements. Si la capsule du personnage avance, tout ce qui y est attaché avance avec elle. Voici la structure du personnage du template Third Person :

  • CapsuleComponentRoot Component : gère la collision avec le décor
    • ArrowComponentIndique la direction « avant » (visible uniquement dans l'éditeur)
    • MeshSkeletalMeshComponent : le modèle animé
    • CameraBoomSpringArmComponent : un bras qui recule si un mur gêne
      • FollowCameraCameraComponent, au bout du bras
  • CharacterMovementComponentActorComponent : pas de transform, donc pas dans l'arbre d'attachement

Pourquoi CreateDefaultSubobject et pas new ?

CreateDefaultSubobject ne s'utilise que dans le constructeur. Il enregistre le composant auprès du système de réflexion pour qu'il apparaisse dans l'éditeur, soit sauvegardé et soit modifiable dans les Blueprints enfants. Le texte passé en paramètre (TEXT("Mesh")) est le nom interne du composant : il doit être unique dans la classe.

Le Gameplay Framework

C'est ici qu'Unreal se distingue des autres moteurs. Plutôt que de vous laisser tout organiser vous-même, il fournit un ensemble de classes avec des rôles bien précis. Ce découpage vient de l'histoire du moteur (les jeux multijoueur Unreal Tournament) : il est pensé pour le réseau dès le départ, mais il est tout aussi utile en solo.

GameMode : l'arbitre

Le AGameModeBase (ou sa version enrichie AGameMode) définit les règles : quelles classes utiliser pour le joueur, comment et où faire apparaître les joueurs, quand la partie est gagnée ou perdue. Il n'existe que sur le serveur : en multijoueur, les clients n'y ont jamais accès (c'est une protection contre la triche).

Chaque niveau peut avoir son propre GameMode (réglage GameMode Override dans World Settings), sinon c'est celui défini dans Project Settings → Maps & Modes qui est utilisé. C'est aussi là que l'on définit les classes par défaut :

  • Default Pawn Class : le personnage du joueur ;
  • Player Controller Class : le contrôleur du joueur ;
  • HUD Class, Player State Class, Game State Class.

GameState : le tableau d'affichage

Le AGameStateBase contient l'état global de la partie que tout le monde doit connaître : temps restant, score des équipes, phase de jeu. Contrairement au GameMode, il est répliqué à tous les clients. Il contient aussi la liste de tous les PlayerState (PlayerArray).

PlayerController : la volonté du joueur

Le APlayerController représente le joueur humain devant son écran. Il reçoit les entrées (clavier, manette), gère la caméra, la souris, l'interface, et transmet les ordres au Pawn qu'il possède. Il survit à la mort du personnage : quand le Pawn est détruit, le Controller reste et peut en posséder un nouveau.

Pawn et Character : le corps

Le APawn est le corps physique dans le monde. Un Pawn peut être n'importe quoi : un humain, une voiture, un vaisseau, une tourelle. ACharacter est un Pawn spécialisé pour les personnages bipèdes : il fournit une capsule de collision, un mesh squelettique et surtout le UCharacterMovementComponent, qui gère marche, saut, chute, nage et vol, avec la prédiction réseau incluse.

PlayerState : la fiche du joueur

Le APlayerState contient les informations publiques d'un joueur que les autres doivent voir : pseudo, score, équipe, ping. Il est répliqué à tous et survit à la mort du Pawn.

GameInstance : la mémoire de la session

La UGameInstance est créée au lancement du jeu et détruite à sa fermeture. C'est le seul objet du framework qui survit aux changements de niveau. Elle est idéale pour les données de session : profil chargé, options, progression entre deux niveaux. Elle n'est pas répliquée : chaque machine a la sienne.

HUD et widgets : l'affichage

La classe AHUD est historique ; aujourd'hui on construit l'interface avec des Widgets UMG (UUserWidget). Le HUD sert encore souvent de point central pour créer et afficher ces widgets. Voir le chapitre Interfaces avec UMG.

La possession : séparer le cerveau du corps

La notion de possession est fondamentale. Un Controller (joueur ou IA) possède un Pawn pour le piloter. Le même Pawn peut donc être contrôlé par un joueur ou par l'IA sans changer une ligne de son code. Et un joueur peut changer de corps : sortir d'un personnage pour monter dans un véhicule, par exemple.

Voici comment récupérer le contrôleur et le personnage du joueur, une opération que vous ferez très souvent :

Depuis le Pawn, on remonte facilement

Dans un Pawn ou un Character : GetController() renvoie son contrôleur et GetPlayerState() son PlayerState. Depuis n'importe quel Actor : GetWorld()->GetAuthGameMode() renvoie le GameMode (sur le serveur seulement) et GetWorld()->GetGameState() le GameState.

Où ranger chaque donnée ?

C'est LA question que tout débutant se pose, et une mauvaise réponse crée des bugs difficiles plus tard (score qui disparaît à la mort du joueur, données perdues au changement de niveau…). Voici un guide de décision :

DonnéeOù la mettrePourquoi
Points de vie actuelsPawn (ou un HealthComponent)Ils disparaissent avec le corps, c'est normal
Score, nombre de killsPlayerStateSurvit à la mort et visible par tous
Temps restant de la mancheGameStateGlobal et visible par tous
Score nécessaire pour gagnerGameModeRègle du jeu, seul le serveur décide
Sensibilité de la sourisPlayerController (+ SaveGame)Propre au joueur local, personne d'autre n'en a besoin
Personnage choisi au menuGameInstanceDoit survivre au chargement du niveau de jeu
Niveaux débloquésSaveGameDoit survivre à la fermeture du jeu

Dans un jeu de tir multijoueur, où stocker le nombre d'éliminations d'un joueur, affiché dans le tableau des scores ?

  • Dans le Character du joueur
  • Dans le GameMode
  • Dans le PlayerState
  • Dans la GameInstance

Le PlayerState survit à la mort du Character (sinon le score serait perdu à chaque mort) et il est répliqué à tous les joueurs (qui doivent voir le tableau des scores). Le GameMode n'existe que sur le serveur, et la GameInstance n'est pas répliquée.

Les Subsystems

Les Subsystems sont des objets créés et détruits automatiquement par le moteur, en même temps que l'objet auquel ils sont rattachés. Ils évitent de surcharger la GameInstance ou le GameMode avec des dizaines de responsabilités : chaque système (quêtes, succès, sauvegarde…) peut avoir son propre Subsystem.

Classe de baseDurée de vieExemple d'usage
UEngineSubsystemToute l'exécution du moteurOutils, services globaux
UGameInstanceSubsystemLa session de jeuSystème de sauvegarde, succès, quêtes
UWorldSubsystemUn monde (un niveau chargé)Gestionnaire d'ennemis, météo du niveau
ULocalPlayerSubsystemUn joueur localEnhanced Input, préférences du joueur

En Blueprint, le Subsystem apparaît automatiquement : faites un clic droit dans le graphe et cherchez « Quest Subsystem ». Pas besoin de cast, pas besoin de l'instancier.

World, Levels et World Partition

Un Level (ou Map, fichier .umap) est un fichier qui contient des Actors placés. Le World est l'objet en mémoire qui contient le niveau chargé et tous ses Actors ; on y accède partout avec GetWorld().

  • Persistent Level : le niveau principal, toujours chargé.
  • Level Streaming : des sous-niveaux chargés et déchargés à la demande (par exemple, l'intérieur d'un bâtiment).
  • World Partition : le système par défaut des grands mondes en UE5. Le monde est découpé automatiquement en cellules d'une grille, chargées selon la distance au joueur. Avec One File Per Actor, chaque Actor est sauvegardé dans son propre fichier, ce qui permet à plusieurs personnes de travailler sur la même carte sans conflit.
  • Changer de niveau : UGameplayStatics::OpenLevel(this, TEXT("NomDuNiveau")) ou le nœud Open Level (by Name). Tout le World est détruit, sauf la GameInstance.

Identifier les classes d'un jeu connu

Prenez un jeu que vous connaissez bien, par exemple Fortnite ou Rocket League. Pour chacune des informations suivantes, indiquez la classe du Gameplay Framework qui devrait la contenir : la voiture/le personnage, la vitesse actuelle, le score des équipes, le pseudo d'un joueur, le temps restant, la règle « le premier à 3 buts gagne », le réglage de la caméra choisi par le joueur.

Voir une solution (Rocket League)
  • La voiture : un Pawn (sans doute une classe dérivée d'APawn avec un composant de mouvement de véhicule).
  • La vitesse actuelle : le Pawn (son composant de mouvement).
  • Le score des équipes et le temps restant : le GameState.
  • Le pseudo, les buts marqués par un joueur : le PlayerState.
  • La règle de victoire : le GameMode.
  • Le réglage de caméra : le PlayerController, sauvegardé dans un SaveGame.

Quel objet est le seul du Gameplay Framework à survivre à un changement de niveau ?

  • Le PlayerController
  • Le GameState
  • La GameInstance
  • Le PlayerState

À l'appel d'OpenLevel, tout le World est détruit avec ses Actors (Controllers, GameState, PlayerStates, Pawns). Seule la GameInstance, et ses Subsystems, persistent pendant toute la session.

À retenir

  • Tout hérite de UObject ; tout ce qui est dans le monde est un AActor.
  • Un Actor tire sa position de son Root Component et ses capacités de ses Components.
  • Le GameMode fixe les règles (serveur), le GameState partage l'état de la partie, le PlayerState l'état d'un joueur.
  • Le PlayerController possède un Pawn : on sépare la volonté du joueur de son corps.
  • La GameInstance survit aux changements de niveau ; le SaveGame survit à la fermeture du jeu.
  • Les Subsystems permettent d'organiser proprement les systèmes globaux.
