C++ pour Unreal : les bases

Le C++ d'Unreal n'est pas tout à fait le C++ des manuels : il est enrichi de macros, de types maison et d'un système de réflexion qui le relie à l'éditeur et aux Blueprints. Ce chapitre vous donne les rappels de C++ indispensables, puis tout ce qu'Unreal ajoute par-dessus, pour écrire vos premières classes avec confiance.

Dans ce chapitre

  • Comprendre pourquoi et comment le C++ et les Blueprints travaillent ensemble
  • Réviser les notions de C++ indispensables : classes, héritage, pointeurs, références, const
  • Lire et écrire une classe Unreal complète : UCLASS, GENERATED_BODY, UPROPERTY, UFUNCTION
  • Utiliser les types du moteur : FString, FName, FText, TArray, TMap, TSet
  • Créer des objets, journaliser, déboguer et organiser son code en modules

Pourquoi le C++ dans Unreal ?

Unreal propose deux façons de programmer : les Blueprints (scripting visuel, voir Blueprints) et le C++. Ce ne sont pas des concurrents : les projets professionnels utilisent presque toujours les deux. Le C++ apporte quatre choses que les Blueprints n'offrent pas, ou mal :

Performance
Le C++ est compilé en code machine. Une boucle sur 10 000 éléments, un algorithme de recherche de chemin ou un calcul exécuté à chaque frame sont nettement plus rapides qu'en Blueprint, dont chaque nœud passe par une machine virtuelle.
Accès complet au moteur
Seule une partie de l'API est exposée aux Blueprints. En C++, vous pouvez tout utiliser, hériter de n'importe quelle classe et surcharger ses fonctions virtuelles.
Travail en équipe
Un fichier texte se compare (diff), se fusionne (merge) et se relit dans Git. Un Blueprint est un fichier binaire : deux personnes ne peuvent pas le modifier en même temps.
Architecture
Classes de base, interfaces, systèmes réutilisables entre plusieurs projets : le C++ structure mieux les gros projets.

C++ et Blueprint : un duo

La règle d'or chez Epic et dans la plupart des studios : la logique et les données de base en C++, le contenu et les réglages en Blueprint. Vous écrivez une classe C++ AWeaponBase qui sait tirer et recharger, et qui expose ses variables et fonctions. Puis vous créez des Blueprints enfants (BP_Rifle, BP_Shotgun) dans lesquels un game designer choisit le mesh, les sons, les dégâts, sans toucher au code.

Plutôt en C++

  • Classes de base du gameplay (personnage, arme, ennemi)
  • Systèmes : inventaire, sauvegarde, santé, réseau
  • Calculs lourds ou exécutés à chaque frame
  • Tout ce qui doit être relu et versionné

Plutôt en Blueprint

  • Choix des assets (meshes, sons, matériaux, effets)
  • Réglage des valeurs par les designers
  • Scripts de niveau, cinématiques, prototypes
  • Réactions visuelles à des événements C++

Rappels de C++ essentiels

Cette section ne remplace pas un cours de C++, mais elle couvre ce que vous croiserez dans chaque fichier Unreal. Si une notion vous est inconnue, prenez le temps de l'expérimenter dans un petit projet.

Types, fonctions et classes

Une classe regroupe des données (les membres) et des fonctions qui les manipulent (les méthodes). Les spécificateurs d'accès contrôlent qui peut y toucher : public (tout le monde), protected (la classe et ses enfants), private (la classe seule).

Pourquoi séparer .h et .cpp

Chaque classe est découpée en deux fichiers. Le header (.h) contient la déclaration : le « contrat » de la classe (ses membres, les signatures de ses fonctions). Le fichier source (.cpp) contient la définition : le corps des fonctions.

La raison est mécanique : #include copie littéralement le contenu d'un fichier dans un autre. Les autres classes n'ont besoin que du contrat pour vous utiliser, donc elles incluent votre .h. Conséquence pratique très importante : modifier un .cpp ne recompile que ce fichier, alors que modifier un .h recompile tous les fichiers qui l'incluent, directement ou indirectement. Dans un gros projet, la différence se compte en minutes.

Héritage, virtual et override

L'héritage permet de créer une classe à partir d'une autre : elle récupère tout ce que possède la classe parente et peut le spécialiser. Une fonction marquée virtual peut être redéfinie par les classes enfants ; le mot-clé override demande au compilateur de vérifier que vous redéfinissez bien une fonction existante (une faute de frappe devient une erreur de compilation au lieu d'un bug silencieux).

Dans Unreal, vous n'écrirez presque jamais FEnemy::GetDamage() : la macro GENERATED_BODY() définit automatiquement Super, un alias vers la classe parente. On écrit donc Super::BeginPlay(), Super::Tick(DeltaTime), etc.

Pointeurs et références

Une variable occupe une case en mémoire, repérée par une adresse. Un pointeur (T*) est une variable qui contient une adresse : il « pointe » vers un objet, peut changer de cible, et peut ne pointer sur rien (nullptr). Une référence (T&) est un autre nom pour une variable existante : elle est liée une fois pour toutes et ne peut pas être nulle.

Le crash numéro un des débutants

Utiliser -> sur un pointeur nul fait planter l'éditeur instantanément (« Access violation reading location 0x0000… »). Testez toujours un pointeur qui peut être nul avant de vous en servir : résultat d'un Cast, d'une recherche, d'une variable assignée dans l'éditeur. Pour les objets Unreal, préférez IsValid(Ptr), qui vérifie aussi que l'objet n'est pas en cours de destruction (voir C++ avancé).

const, auto, boucles et lambdas

  • const sur une variable : elle ne changera plus. Sur une méthode (float GetHealth() const) : la méthode promet de ne pas modifier l'objet. Sur un paramètre (const FString&) : la fonction lit sans copier ni modifier.
  • auto laisse le compilateur déduire le type. Pratique pour les types longs, mais le standard d'Epic recommande d'écrire le type quand il aide à la lecture.
  • La boucle range-for parcourt un conteneur sans indice : for (AActor* Actor : Actors).
  • Une lambda est une petite fonction anonyme, écrite sur place. Les crochets indiquent ce qu'elle capture : [this], [Damage] (copie), [&Total] (référence).

Remarque : quand on trie un TArray de pointeurs avec Sort, Unreal passe au prédicat des références vers les objets pointés, d'où const AActor& ci-dessus.

Déclarations anticipées ou includes

Dans un header, si vous ne manipulez un type que par pointeur ou référence, vous n'avez pas besoin de connaître sa définition complète : une déclaration anticipée (forward declaration) suffit. On inclut le vrai header seulement dans le .cpp, là où l'on appelle ses fonctions.

Temps de compilation

Prenez le réflexe : déclarations anticipées dans les .h, includes dans les .cpp. Le header de la classe parente, lui, doit toujours être inclus (le compilateur doit connaître la classe dont on hérite), de même que les types utilisés par valeur (une struct membre, un enum).

Anatomie d'une classe Unreal

Voici le header complet d'un bonus de soin. Les lignes surlignées sont celles qu'Unreal ajoute au C++ classique ; chacune a un rôle précis.

Oublier Super::

Surcharger BeginPlay, Tick ou EndPlay sans appeler Super:: casse des comportements de manière silencieuse : par exemple, l'événement BeginPlay des Blueprints enfants ne se déclenche plus, ou les composants ne sont pas initialisés. Mettez l'appel à Super:: en première ligne (en dernière ligne pour EndPlay est aussi courant).

Réflexion et Unreal Header Tool

Le C++ standard n'a pas de réflexion : à l'exécution, un programme ne peut pas lister les variables d'une classe ni appeler une fonction à partir de son nom. Unreal comble ce manque avec un outil, l'Unreal Header Tool (UHT), qui lit vos headers avant le compilateur, repère les macros UCLASS, UPROPERTY, UFUNCTION, et génère le code qui décrit vos classes au moteur.

Ce que la réflexion rend possible :

Éditeur

Panneau Details

Les UPROPERTY apparaissent et se règlent dans l'éditeur, avec catégories, bornes et infobulles.

Blueprint

Nœuds et variables

Les classes, fonctions et variables marquées deviennent utilisables et dérivables en Blueprint.

Mémoire

Garbage collection

Le moteur suit les pointeurs UPROPERTY pour savoir quels objets sont encore utilisés.

Données

Sérialisation et réseau

Sauvegarde des assets et niveaux, réplication des propriétés, lecture des fichiers .ini.

Les macros ont des règles

UHT n'est pas un compilateur complet : les UPROPERTY et UFUNCTION doivent se trouver dans le header, dans une classe UCLASS ou une struct USTRUCT. UHT ne gère qu'un sous-ensemble des types C++ (pas de std::vector, pas de unsigned int exposé au Blueprint, etc.). Les erreurs UHT apparaissent avant la compilation, avec le nom du fichier et la ligne.

UPROPERTY : exposer des variables

Une variable marquée UPROPERTY(...) est connue du moteur. Les spécificateurs entre parenthèses décident de sa visibilité dans l'éditeur, dans les graphes Blueprint, et de son comportement (sauvegarde, réseau, configuration).

Valeurs par défaut et instances

Toute classe Unreal possède un objet modèle, le CDO (Class Default Object), construit avec votre constructeur C++. Un Blueprint enfant a ses propres valeurs par défaut (le bouton Class Defaults de l'éditeur de Blueprint), qui écrasent celles du C++. Enfin, chaque instance posée dans le niveau peut à son tour écraser certaines valeurs. Les spécificateurs Edit… disent à quel étage la modification est autorisée.

VisibleAnywhere pour les pointeurs de composants

Déclarez les composants avec VisibleAnywhere, pas EditAnywhere. « Visible » porte sur le pointeur : on ne peut pas remplacer le composant par un autre, mais toutes les propriétés du composant (mesh, matériau, rayon…) restent modifiables dans le panneau Details. Avec EditAnywhere, l'éditeur propose de changer le pointeur lui-même, ce qui mène à des composants perdus ou des Blueprints corrompus.

UFUNCTION : exposer des fonctions

De la même manière, UFUNCTION(...) rend une fonction visible du moteur. C'est indispensable pour l'appeler depuis un Blueprint, la lier à un événement dynamique (AddDynamic) ou en faire une fonction réseau.

SpécificateurEffetNœud Blueprint

Côté Blueprint enfant, ces déclarations deviennent des nœuds : l'événement On Damage Taken se place dans l'Event Graph, Get Health Percent est un nœud pur et Activate Shield un nœud d'appel classique.

Implementable ou Native ?

Choisissez BlueprintImplementableEvent quand le C++ n'a rien à faire par défaut (jouer un effet, un son). Choisissez BlueprintNativeEvent quand il existe un comportement par défaut raisonnable que certains Blueprints voudront remplacer. Dans les deux cas, le C++ appelle la fonction par son nom normal, jamais _Implementation directement.

USTRUCT et UENUM

Une struct regroupe des données sans comportement complexe : les statistiques d'une arme, une ligne de Data Table, une récompense. Une énumération représente un choix parmi une liste fermée : type d'arme, état d'une porte, difficulté. Exposées au moteur, elles deviennent utilisables dans l'éditeur et en Blueprint.

  • Le préfixe F est obligatoire pour une USTRUCT, E pour une UENUM.
  • GENERATED_BODY() est aussi requis dans une struct ; elle n'a pas besoin de macro _API tant qu'elle n'a pas de fonctions utilisées depuis d'autres modules.
  • UMETA(DisplayName = "...") change le nom affiché dans l'éditeur sans changer le nom C++.
  • Une USTRUCT ne peut pas contenir de UFUNCTION : la logique reste dans les classes.

Types de base et chaînes de caractères

Nombres et booléens

Unreal définit ses propres types numériques pour garantir la même taille sur toutes les plateformes : int32 (l'entier standard), uint8 (octet, 0 à 255, utilisé pour les énumérations), int64 (grands nombres : argent d'un jeu de gestion, horodatages). N'utilisez pas int ou long nus dans les déclarations exposées.

Côté décimaux, float (32 bits) reste le type courant des variables de gameplay, mais depuis UE5 les types mathématiques comme FVector, FRotator et FTransform utilisent des double (64 bits) : c'est ce qui permet les très grands mondes (Large World Coordinates). Les variables « Float » des Blueprints sont d'ailleurs des doubles en interne. Si vous avez besoin d'un vecteur en float, il existe FVector3f.

Les booléens portent le préfixe b : bIsDead, bCanJump. L'éditeur l'enlève automatiquement à l'affichage (« Is Dead »).

FString, FName et FText

TypeNatureUsage typique
FStringChaîne modifiable, allouée dynamiquementManipulation, concaténation, logs, débogage, chemins de fichiers

L'étoile devant les FString

FString::Printf et UE_LOG attendent un TCHAR* pour %s. Passer un FString sans * compile parfois mais affiche n'importe quoi ou plante. Écrivez toujours *MaChaine, et *Name.ToString() pour un FName.

Conteneurs : TArray, TMap, TSet

Unreal fournit ses propres conteneurs, compatibles avec la réflexion (donc utilisables en UPROPERTY et en Blueprint), à la place de std::vector ou std::map.

TArray : le tableau dynamique

TMap et TSet

Un TMap associe une clé unique à une valeur (un dictionnaire) ; un TSet est un ensemble de valeurs uniques. Les deux offrent une recherche quasi instantanée, quelle que soit leur taille, mais ne garantissent aucun ordre.

Ne jamais retirer pendant un parcours range-for

Modifier un TArray pendant qu'une boucle for (X : Array) le parcourt déclenche une assertion (« Array has changed during ranged-for iteration ») ou, en Shipping, un comportement indéfini. Parcourez à l'envers avec des indices, ou utilisez RemoveAll.

Créer des objets

En C++ classique on crée un objet avec new. Pour un UObject, c'est interdit : le moteur doit enregistrer l'objet (réflexion, garbage collector, monde). Il existe trois façons de créer des objets Unreal, chacune pour un usage précis.

FonctionPour créerQuand
CreateDefaultSubobject<T>(TEXT("Nom"))Un composant ou sous-objet par défautUniquement dans le constructeur
NewObject<T>(Outer)Un UObject qui n'est pas un Actor (objet d'inventaire, quête…)À l'exécution
GetWorld()->SpawnActor<T>(...)Un Actor dans le mondeÀ l'exécution (BeginPlay, événements…)

Cast, IsA et CastChecked

Un cast convertit un pointeur vers un type plus précis. Cast<T> vérifie le type réel de l'objet et renvoie nullptr s'il ne correspond pas : c'est sûr, mais il faut tester le résultat.

Logs et débogage

UE_LOG et ses niveaux

UE_LOG(Catégorie, Verbosité, TEXT("format"), arguments...) écrit dans l'Output Log de l'éditeur (menu Window → Output Log) et dans le fichier Saved/Logs/MyGame.log. LogTemp est une catégorie fourre-tout, pratique pour démarrer.

VerbositéEffet
FatalÉcrit le message puis arrête le programme (crash volontaire)
ErrorEn rouge
WarningEn jaune
DisplayToujours affiché, y compris dans la console
LogNiveau normal, visible dans l'Output Log
Verbose, VeryVerboseMasqués par défaut : informations détaillées à activer au besoin

Pour filtrer facilement vos messages, créez votre propre catégorie : déclarée dans un header, définie dans un .cpp.

check et ensure

Les assertions vérifient une hypothèse du programmeur. Elles signalent un bug le plus tôt possible, au lieu de laisser le jeu continuer dans un état incohérent.

Règle simple : check pour « ceci ne peut pas arriver, continuer serait pire qu'un crash », ensure pour « ceci ne devrait pas arriver, mais on peut s'en remettre ». Attention : l'expression d'un check n'est pas évaluée en Shipping, n'y mettez jamais d'appel qui a un effet nécessaire (utilisez verify pour ça).

Public ou Private ? Une dépendance publique est transmise aux modules qui dépendent du vôtre ; une dépendance privée reste interne. Pour un module de jeu unique, la différence est faible : mettez en public ce dont vos headers ont besoin, le reste en privé.

« unresolved external symbol » = module manquant

L'erreur de l'éditeur de liens LNK2019: unresolved external symbol (ou undefined reference sous Linux) signifie presque toujours que le header a été trouvé mais pas le code compilé : ajoutez le module de la classe utilisée dans Build.cs. Le nom du module figure en haut de la page de documentation de chaque classe (rubrique Module).

Compiler sans douleur

  1. Modification dans un .cppUtilisez Live Coding : Ctrl+Alt+F11 dans l'éditeur (ou le bouton en bas à droite). Le code est recompilé et injecté sans fermer l'éditeur.
  2. Modification dans un .hNouvelle UPROPERTY, nouvelle UFUNCTION, nouvelle classe, changement de spécificateurs : fermez l'éditeur, compilez depuis l'IDE (configuration Development Editor), puis relancez. Live Coding sait parfois gérer ces cas selon votre version, mais c'est la première source de Blueprints corrompus.
  3. Fichiers ajoutés hors de l'IDERégénérez les fichiers de projet : clic droit sur le .uproject → Generate Visual Studio project files (Windows), ou depuis l'éditeur dans le menu Tools (« Refresh … Project », le libellé dépend de l'IDE).
  4. Erreurs incompréhensiblesFermez l'éditeur et l'IDE, supprimez les dossiers Binaries et Intermediate du projet (ils sont entièrement régénérés), régénérez les fichiers de projet et recompilez. Ne touchez pas à Content, Config ni Source.

Le standard de code d'Epic

Cherchez « Coding Standard » dans la documentation d'Unreal. L'essentiel : PascalCase pour tout (MaxHealth, GetHealth()), préfixes de types (A, U, F, E, I, T), b pour les booléens, accolades sur leur propre ligne, TEXT() autour des littéraux, types Unreal plutôt que la bibliothèque standard. Suivre ce standard rend votre code lisible par n'importe quel développeur Unreal.

Créez ensuite un Blueprint enfant BP_RotatingPlatform (clic droit sur la classe C++ dans le Content Browser → Create Blueprint class based on…), choisissez un mesh, puis utilisez les nœuds générés :

Où doit se trouver la ligne #include "MaClasse.generated.h" ?

  • En premier, avant CoreMinimal.h
  • Dans le fichier .cpp
  • En dernier parmi les includes du header
  • N'importe où, l'ordre n'a pas d'importance

L'Unreal Header Tool exige que le header généré soit le dernier include du fichier .h : il contient des macros qui dépendent de tout ce qui a été inclus avant. Sinon, UHT s'arrête avec une erreur explicite.

Vous voulez que le designer règle les dégâts d'un type d'ennemi dans son Blueprint, mais pas ennemi par ennemi dans le niveau. Quel spécificateur choisir ?

  • EditAnywhere
  • EditDefaultsOnly
  • EditInstanceOnly
  • VisibleAnywhere

EditDefaultsOnly n'autorise la modification que dans les Class Defaults : tous les ennemis de ce Blueprint partagent la valeur. EditAnywhere permettrait aussi de la changer sur chaque instance.

Que renvoie Ammo.Find(TEXT("Rocket")) sur un TMap<FName, int32> qui ne contient pas cette clé ?

  • 0
  • -1 (INDEX_NONE)
  • nullptr
  • Le programme plante

TMap::Find renvoie un pointeur vers la valeur, ou nullptr si la clé est absente. Il faut donc tester le résultat avant de le déréférencer. FindRef renvoie une copie (valeur par défaut si absente) et FindOrAdd crée l'entrée.

Un ramassable d'arme exposé au Blueprint

Créez une énumération EWeaponType et une struct FWeaponData (nom affiché, type, dégâts, cadence de tir, taille du chargeur) utilisables en Blueprint. Puis créez un Actor AWeaponPickup : une sphère de collision racine, un mesh sans collision, une variable FWeaponData réglable dans l'éditeur, une fonction pure GetDamagePerSecond, et un événement OnPickedUp implémenté en Blueprint quand un personnage le touche. Créez enfin BP_Pickup_Shotgun avec ses propres valeurs.

Voir la solution
