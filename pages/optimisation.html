Débogage & optimisation

Un jeu qui plante ou qui saccade ne sera jamais agréable, quelle que soit la qualité de son gameplay. Ce chapitre vous apprend d'abord à trouver les bugs (débogueur, crashs, logs, outils visuels), puis à rendre le jeu fluide avec méthode. La règle d'or de l'optimisation tient en deux mots : on mesure, on ne devine pas.

Dans ce chapitre

  • Déboguer le C++ pas à pas et comprendre un crash
  • Utiliser les logs, les variables console et les outils de débogage visuel
  • Raisonner en budget de frame et trouver le goulot d'étranglement avec stat unit
  • Profiler avec les commandes stat et Unreal Insights
  • Appliquer les optimisations CPU, GPU, mémoire et chargement qui comptent vraiment

Déboguer le C++ avec l'IDE

Un débogueur permet de mettre le programme en pause sur une ligne précise, puis d'inspecter les variables et d'avancer instruction par instruction. C'est infiniment plus efficace que d'ajouter des logs au hasard. Dans Visual Studio ou Rider, choisissez votre projet de jeu comme projet de démarrage, puis lancez avec F5 : l'éditeur démarre avec le débogueur attaché. Pour un éditeur déjà ouvert, utilisez Debug → Attach to Process (Ctrl+Alt+P dans Visual Studio) et choisissez UnrealEditor.exe.

Points d'arrêt, espions et pile d'appels

Point d'arrêt (F9)
L'exécution s'arrête quand elle atteint la ligne. Tout l'éditeur se fige : c'est normal, il attend que vous repreniez avec F5.
Point d'arrêt conditionnel
Clic droit sur le point d'arrêt → Conditions : par exemple Health <= 0.f ou un nombre de passages. Indispensable quand le code s'exécute 60 fois par seconde pour 200 ennemis. Préférez des conditions sur des nombres ou des pointeurs : les FString se comparent mal dans le débogueur.
Pas à pas
F10 exécute la ligne (step over), F11 entre dans la fonction appelée (step into), Shift+F11 en ressort (step out). Raccourcis de Visual Studio ; Rider propose les mêmes commandes selon le schéma clavier choisi.
Espions (Watch, Locals, Autos)
Fenêtres qui affichent la valeur des variables. Unreal fournit un fichier natvis pour que FString, TArray ou FName s'affichent lisiblement.
Pile d'appels (Call Stack)
La chaîne de fonctions qui a mené jusqu'ici : « qui m'a appelé ? ». Double-cliquez sur une ligne pour voir le code et les variables de ce niveau.

Symboles et variables « optimisées »

Pour voir les noms de fonctions du moteur dans la pile d'appels et entrer dans son code, installez les Editor symbols for debugging : dans l'Epic Games Launcher, bibliothèque → flèche à côté de la version du moteur → Options. Comprendre un crash

Quand l'éditeur ou le jeu plante, la fenêtre du Crash Reporter affiche la pile d'appels. Lisez-la de haut en bas et cherchez la première ligne qui appartient à votre module (par exemple UnrealEditor-MyGame.dll!AEnemy::Attack() [Enemy.cpp:87]) : c'est presque toujours là que se trouve le bug. Tous les fichiers utiles sont dans le dossier Saved du projet (pour un jeu packagé, dans son propre dossier Saved ou dans %LOCALAPPDATA%, selon la configuration) :

  • Saved/à la racine du projet
    • Logs/MyGame.log (session en cours) et les MyGame-backup-….log des sessions précédentes
    • Crashes/un sous-dossier par crash
      • UECC-Windows-…/
        • CrashContext.runtime-xmlpile d'appels, machine, version du moteur
        • MyGame.logle log jusqu'à l'instant du crash
        • UEMinidump.dmps'ouvre dans Visual Studio ; avec les fichiers .pdb du build, on retrouve la pile et les variables

Les trois crashs les plus fréquents

Pointeur nul (« Access violation reading location 0x0000000000000000 ») : testez vos pointeurs avec IsValid(). Index hors limites (« Array index out of bounds ») : vérifiez avec IsValidIndex(). Objet détruit par le garbage collector : un pointeur vers un UObject stocké sans UPROPERTY() n'empêche pas sa destruction (voir C++ avancé). Et conservez toujours les .pdb des builds que vous distribuez : sans eux, les rapports de crash des joueurs sont illisibles.

check, ensure et verify

Les assertions vérifient qu'une condition qui devrait toujours être vraie l'est bien. Elles transforment un bug silencieux en arrêt immédiat, à l'endroit exact du problème :

MacroSi la condition est fausseEn ShippingUsage
check(x), checkf(x, fmt, …)Crash immédiat avec message et pile d'appelsSupprimé : l'expression n'est même pas évaluéeInvariants absolus, bugs de programmation
verify(x)Crash, comme checkL'expression est évaluée mais pas testéeQuand l'expression a un effet nécessaire (un appel de fonction)
ensure(x), ensureMsgf(x, fmt, …)Erreur + pile d'appels dans le log (une fois par emplacement), le jeu continue ; renvoie le résultatPlus de rapport, mais l'expression est évaluée et renvoyéeSituations anormales mais récupérables
checkNoEntry()Crash si cette ligne est atteinteSuppriméBranche impossible (le default d'un switch)

Avec le débogueur attaché, un ensure qui échoue s'arrête comme un point d'arrêt : vous inspectez la situation, puis vous continuez. Ne mettez jamais dans un check une expression qui doit s'exécuter en Shipping (check(Init()) disparaîtrait, appel compris) : utilisez verify.

Les fonctions DrawDebug* dessinent dans le monde (elles disparaissent automatiquement des builds Shipping), AddOnScreenDebugMessage écrit à l'écran (comme Print String), et une variable console permet d'activer tout cela à la demande, sans recompiler :

Le budget de frame

On parle souvent en images par seconde (fps), mais les développeurs raisonnent en millisecondes par frame. À 60 fps, tout le travail d'une image (gameplay, physique, animation, rendu) doit tenir en 16,7 ms : c'est le budget de frame.

CibleBudget par frameContexte typique
30 fps33,3 msMode « qualité » sur console, jeux lents
60 fps16,7 msStandard pour l'action sur PC et console
120 fps8,3 msModes performance, jeux compétitifs
144 fps6,9 msÉcrans haute fréquence, e-sport

Pourquoi les millisecondes ? Parce que les fps trompent : passer de 60 à 50 fps coûte 3,3 ms, alors que passer de 30 à 20 fps en coûte 16,7. Un gain de « 10 fps » ne veut rien dire ; un gain de 2 ms, si.

Les threads d'une frame

Unreal répartit le travail sur plusieurs threads qui fonctionnent en parallèle, décalés d'une frame (un pipeline) : pendant que le GPU dessine une image, le render thread prépare la suivante et le game thread simule déjà celle d'après. Conséquence majeure : la durée d'une frame est fixée par l'étage le plus lent, pas par la somme. Optimiser un étage qui n'est pas le plus lent ne fait gagner aucune image par seconde.

Lire stat unit

Tapez stat unit dans la console : quelques lignes apparaissent en haut à droite de l'écran, en millisecondes.

Frame
Durée totale d'une image : ce que le joueur ressent.
Game
Temps du game thread (gameplay, Tick, Blueprints, physique, animation, IA).
Draw
Temps du render thread (visibilité, préparation des commandes de dessin).
RHIT
Temps du RHI thread (soumission des commandes à l'API graphique).
GPU
Temps de travail de la carte graphique pour cette image. Selon la version, d'autres lignes s'ajoutent (résolution dynamique, nombre de draw calls et de primitives, mémoire).

La règle : la valeur la plus proche de Frame désigne le goulot d'étranglement. Si Frame est nettement au-dessus de toutes les autres, quelque chose attend : synchronisation verticale (r.VSync), limite d'images (t.MaxFPS), ou éditeur ralenti parce qu'il n'a pas le focus (option Use Less CPU when in Background des Editor Preferences).

stat unit affiche Frame 33 ms, Game 9 ms, Draw 7 ms, GPU 32 ms. Avec r.ScreenPercentage 50, le temps GPU tombe à 14 ms. Quelle piste suivre ?

  • Réduire le nombre d'Actors qui utilisent Tick
  • Fusionner des Actors pour réduire les draw calls
  • Réduire le coût par pixel : résolution interne et upscaling, post-process, Lumen, ombres, translucidité
  • Convertir les Blueprints en C++

GPU est la valeur la plus proche de Frame : le GPU est le goulot. Diviser le nombre de pixels par quatre divise presque son temps par deux : le coût dépend surtout du nombre de pixels. Le game thread (9 ms) n'est pas en cause, l'optimiser ne changerait rien.

Le test de r.ScreenPercentage est le plus utile de tous quand le GPU est en cause. Si le temps GPU chute fortement, le jeu est limité par les pixels : le coût vient de ce qui est calculé pour chaque pixel (post-process, éclairage, ombres filtrées, translucidité, matériaux complexes). S'il bouge à peine, le coût vient de la géométrie ou de passes fixes : trop de triangles sans Nanite, trop d'objets dans les ombres, trop de draw calls.

Unreal Insights

Unreal Insights est le profileur principal d'Unreal. Le jeu enregistre une trace (fichier .utrace) de tout ce qui se passe, et l'application Insights permet ensuite de l'explorer : durée de chaque fonction sur chaque thread, frame par frame.

  1. Lancer Unreal InsightsL'exécutable se trouve dans Engine/Binaries/Win64/UnrealInsights.exe (selon la version, il est aussi accessible depuis l'éditeur). Il démarre un serveur local qui collecte les traces.
  2. Lancer le jeu avec la traceAjoutez les canaux voulus en ligne de commande, comme ci-dessous. Dans l'éditeur, le menu Trace en bas à droite de la barre d'état permet aussi de choisir les canaux et de démarrer un enregistrement (son contenu varie selon la version).
  3. Reproduire le problèmeJouez le passage qui saccade. Ajoutez au besoin des repères dans le code avec TRACE_BOOKMARK(TEXT("Boss apparu")).
  4. AnalyserDans Insights, double-cliquez sur la session pour ouvrir Timing Insights, sélectionnez une frame lente dans le graphique et lisez les blocs les plus longs du thread en cause.
Timing Insights
La vue principale : graphique des frames, une piste par thread (GameThread, RenderThread, RHIThread, GPU), et un tableau des timers triable par temps inclusif ou exclusif.
Memory Insights
Allocations mémoire par catégorie et par pile d'appels, pour trouver fuites et pics. Demande les canaux mémoire (par exemple -trace=default,memory, selon la version).
Networking Insights
Paquets, bande passante par Actor et par propriété répliquée (voir Réseau & multijoueur). Demande le canal net et, selon la version, l'option -NetTrace=1.

Instrumenter votre code

Par défaut, Insights montre les grandes fonctions du moteur. Pour voir le détail de votre code, entourez les portions intéressantes de scopes nommés :

Optimiser le CPU

Tick : le premier suspect

Chaque Actor qui « tick » coûte quelque chose à chaque frame, même s'il ne fait presque rien. Trois cents Blueprints qui vérifient une condition dans Event Tick, c'est souvent plusieurs millisecondes perdues. Les remèdes, du plus simple au plus avancé : désactiver le Tick quand il ne sert pas (bCanEverTick = false, ou décocher Start with Tick Enabled dans les Class Defaults) et ne l'activer que pendant une animation (SetActorTickEnabled) ; l'espacer avec TickInterval (ou SetActorTickInterval), 0,2 s suffisant pour une tourelle qui cherche une cible ; le remplacer par un timer ou un événement (overlap, delegate) ; enfin le moduler selon l'importance, avec le plugin Significance Manager qui calcule l'importance de chaque objet (distance, visibilité) pour ralentir la mise à jour des objets lointains.

Réagir plutôt que surveiller

Le pire motif, très courant en Blueprint : chercher tous les ennemis du niveau avec Get All Actors Of Class à chaque frame. Ce nœud parcourt les Actors du monde : appelé 60 fois par seconde, il coûte cher pour rien. La bonne approche : mettre en cache (chaque ennemi s'enregistre auprès d'un gestionnaire ou d'un Subsystem dans son BeginPlay et se retire dans son EndPlay) et espacer le traitement avec un timer.

Object pooling

Créer un Actor (SpawnActor) est coûteux : allocation, enregistrement des composants, BeginPlay… puis, à sa destruction, du travail pour le garbage collector. Une mitrailleuse qui crée et détruit 20 projectiles par seconde provoque des micro-saccades. Le pooling consiste à créer les objets une fois pour toutes au chargement, puis à les recycler : on les cache au lieu de les détruire, et on les réutilise au tir suivant.

Le personnage ou l'arme possède un UProjectilePoolComponent et appelle FireProjectile au lieu de SpawnActor. Le même principe s'applique aux effets d'impact, aux douilles, aux ennemis d'une vague ou aux nombres de dégâts flottants. En multijoueur, recycler des Actors répliqués est plus délicat : réservez d'abord le pooling aux objets locaux ou cosmétiques.

Blueprint ou C++ ?

Chaque nœud Blueprint passe par une machine virtuelle : pour de la logique événementielle (un bouton, une porte, une quête), le surcoût est négligeable. Il devient visible dans les boucles lourdes : des milliers d'itérations par frame, des calculs mathématiques en masse, du tri. Déplacez alors ce cœur de calcul dans une fonction C++ BlueprintCallable que le Blueprint appelle, et gardez le reste en Blueprint. Mesurez avant : Insights montre les fonctions Blueprint coûteuses.

Chargement asynchrone

Charger un gros asset de manière synchrone (le Blueprint attend le disque) fige le jeu. Avec une référence souple (TSoftObjectPtr, voir plus bas), on lance le chargement en arrière-plan et on est prévenu quand il est terminé. En Blueprint, c'est le nœud Async Load Asset.

Physique, animation et IA

Physique
Limitez le nombre de corps simulés en même temps, utilisez des collisions simples (boîtes, capsules) plutôt que des meshes complexes, et laissez les objets immobiles s'endormir.
Animation
Les personnages lointains n'ont pas besoin d'une animation à pleine fréquence : activez les Update Rate Optimizations (URO) du Skeletal Mesh, et réglez VisibilityBasedAnimTickOption pour ne pas animer ce qui est hors écran. Gardez la logique des Anim Blueprints compatible avec la mise à jour multithread (fonctions thread safe, voir Animation).
IA
Espacez les services des Behavior Trees, réduisez la fréquence de la perception, et ne faites réfléchir à pleine vitesse que les ennemis proches du joueur.

Optimiser le GPU

Draw calls et instancing
Chaque mesh visible, multiplié par chacun de ses matériaux, coûte au moins un draw call (un ordre de dessin) par passe. Des milliers de draw calls chargent le render thread et le RHI thread. Pour des objets identiques répétés (arbres, rochers, caisses), utilisez un Instanced Static Mesh (ISM : N copies en un seul ordre) ou un Hierarchical ISM (HISM : ajoute culling et LOD par groupe, c'est ce qu'utilise le Foliage). L'outil Merge Actors fusionne aussi plusieurs meshes statiques en un seul.
Nanite
La géométrie virtualisée d'UE5 : des meshes de millions de triangles, un LOD automatique et très peu de draw calls. À activer par Static Mesh. Elle ne prend pas en charge les matériaux translucides, et certains cas (matériaux masqués, World Position Offset, meshes animés) ont un coût ou un statut qui dépend de la version : vérifiez la documentation de la vôtre.
Overdraw et translucidité
Chaque couche translucide (fumée, verre, particules) recalcule les pixels qu'elle recouvre. Quelques grosses particules plein écran suffisent à faire exploser le temps GPU. Le mode de vue Optimization Viewmodes → Shader Complexity (Alt+8) colore le coût par pixel : du vert (bon) au rouge puis au blanc (très cher).
Ombres
UE5 utilise par défaut les Virtual Shadow Maps. Leur coût grandit avec le nombre de lumières qui projettent des ombres et avec les objets qui bougent (le cache doit être recalculé). Décochez Cast Shadows sur les petites lumières décoratives et réduisez leur rayon d'atténuation.
Lumen
L'illumination globale et les réflexions dynamiques ont un coût élevé, réglable par les niveaux de qualité (Scalability : sg.GlobalIlluminationQuality, sg.ReflectionQuality). Selon la version, Lumen n'est actif qu'aux niveaux élevés : proposez des réglages graphiques aux joueurs.
Résolution et TSR
Le Temporal Super Resolution calcule l'image à une résolution interne plus basse puis la reconstruit : c'est le levier le plus puissant quand le jeu est limité par les pixels. La résolution dynamique ajuste ce pourcentage automatiquement pour tenir le budget.
Post-process
Bloom, profondeur de champ, flou de mouvement, occlusion ambiante : chacun coûte quelques dixièmes de milliseconde à plusieurs millisecondes en 4K. stat gpu les liste individuellement.
Textures et streaming
Les textures sont chargées à la résolution utile dans un pool de streaming de taille fixe. Le message « Texture streaming pool over budget » signale qu'il est plein : textures floues, puis saccades. Vérifiez avec stat streaming, réduisez la taille maximale des textures secondaires ou augmentez r.Streaming.PoolSize si la mémoire vidéo le permet.
LOD, culling et HLOD
Pour les meshes sans Nanite, générez des LOD (versions simplifiées affichées de loin) dans l'éditeur de Static Mesh. Le moteur élimine déjà ce qui est hors de la caméra ou caché (frustum et occlusion culling) ; un Cull Distance Volume ou la Max Draw Distance d'un composant font disparaître les petits objets lointains. Les HLOD remplacent de grands groupes d'objets lointains par un mesh fusionné simplifié (avec World Partition, via des HLOD Layers).

Mémoire et chargement

Références dures et souples

Une référence dure (un UPROPERTY de type TObjectPtr ou TSubclassOf, une variable Blueprint de type objet ou classe, et même un simple nœud Cast To) oblige le moteur à charger l'asset référencé en même temps que celui qui le référence. Ces chaînes se propagent : charger le joueur peut charger, de cast en cast, la moitié du jeu.

Une référence souple (TSoftObjectPtr, TSoftClassPtr, ou les types Soft Object Reference en Blueprint) ne stocke qu'un chemin : l'asset n'est chargé que lorsque vous le demandez. Pour casser les chaînes de casts, communiquez par interfaces ou par une classe de base C++ légère (sans assets), et chargez le contenu lourd à la demande.

Pour mesurer, faites un clic droit sur un asset dans le Content Browser : Size Map affiche la mémoire et la taille sur disque de l'asset avec tout ce qu'il entraîne, et le Reference Viewer dessine le graphe de ses dépendances. Un personnage dont la Size Map dépasse le gigaoctet a presque toujours une chaîne de références dures à casser.

Asset Manager et garbage collector

L'Asset Manager organise le chargement des contenus importants (niveaux, personnages, objets) sous forme de Primary Assets (par exemple des UPrimaryDataAsset), déclarés dans Project Settings → Asset Manager. Il permet de les charger et décharger explicitement, et sert aussi à découper le jeu packagé en morceaux (chunks).

Le garbage collector parcourt régulièrement les objets pour libérer ceux qui ne sont plus référencés. Avec des centaines de milliers d'objets, ce passage peut provoquer un pic visible dans stat unitgraph. Pour le limiter : créer moins d'objets temporaires (d'où le pooling), et déclencher un nettoyage pendant les écrans de chargement plutôt qu'en plein combat (GEngine->ForceGarbageCollection(true)).

Le premier niveau de votre jeu met longtemps à charger, alors que le boss final n'y apparaît pas. Le Reference Viewer montre que BP_Player référence BP_Boss. Quelle est la cause la plus probable ?

  • Le boss est caché dans le niveau
  • Un nœud Cast To BP_Boss (ou une variable de ce type) dans BP_Player crée une référence dure qui charge le boss et ses assets
  • Les textures du boss sont trop grandes pour le pool de streaming
  • Le garbage collector n'a pas encore libéré le boss

Un Cast To ou une variable typée sur une classe Blueprint est une référence dure : charger BP_Player charge BP_Boss, son mesh, ses animations et tout ce qu'il référence lui-même. Remplacez le cast par une interface ou une classe de base légère, et utilisez des références souples pour le contenu lourd.

Saccades de compilation de shaders

Sur DirectX 12, Vulkan et Metal, le GPU a besoin d'un PSO (Pipeline State Object) pour chaque combinaison de shader et d'états de rendu. S'il est créé au moment où un matériau ou un effet apparaît pour la première fois, le jeu se fige quelques dizaines de millisecondes : c'est la saccade typique « la première fois que j'utilise cette arme ». Deux remèdes complémentaires existent : le PSO precaching, introduit avec UE 5.1 et activé par défaut dans les versions plus récentes, qui prépare les PSO pendant le chargement des assets ; et le cache de PSO empaqueté (bundled PSO cache), enregistré pendant des sessions de test puis livré avec le jeu. Leur configuration exacte dépend de votre version et de la plateforme : consultez la page « PSO Caching » de la documentation.

À ne pas confondre avec le message « Compiling Shaders » de l'éditeur (au premier lancement ou après une modification de matériau) : c'est la compilation des shaders eux-mêmes, mise en cache dans le Derived Data Cache. Elle ralentit le travail dans l'éditeur, pas le jeu packagé.

Profiler au bon endroit

L'éditeur fausse les mesures : son interface, ses autres viewports, les assets non « cookés » et l'exécution en PIE dans le même processus ajoutent du travail qui n'existera pas chez le joueur. Pour un premier tri, lancez le mode Standalone Game (menu Play) ou -game en ligne de commande. Pour des chiffres fiables, profilez un build packagé en configuration Development (stats et console disponibles) ou Test (proche du Shipping, avec les outils de profilage), sur la machine la plus faible que vous visez. Le Shipping, lui, n'a ni console ni stats. Voir Packaging & publication.

Bonnes pratiques

  • Mesurer d'abord, identifier l'étage le plus lent, puis agir sur lui seul
  • Timers, delegates et événements plutôt que du polling en Tick
  • Listes tenues à jour (enregistrement à BeginPlay) et références mises en cache
  • Pool pour les objets créés en grand nombre
  • Références souples et chargement asynchrone pour le contenu lourd

Pièges

  • Optimiser « au feeling », ou uniquement dans l'éditeur
  • Baisser la résolution alors que c'est le game thread qui limite
  • Event Tick partout, Get All Actors Of Class à chaque frame
  • Spawn et Destroy de centaines de projectiles par seconde
  • Des Cast To vers des Blueprints lourds dans tous les sens

Diagnostiquer un profil

Votre jeu d'action doit tenir 60 fps. Dans un build Development packagé, pendant une grosse bataille, stat unit affiche : Game 25 ms, Draw 8 ms, GPU 12 ms. Quel est le goulot d'étranglement ? Que faites-vous, et dans quel ordre ? Que se passera-t-il une fois ce problème réglé ?

Voir la solution

Diagnostic. Frame vaut environ 25 ms (40 fps) : c'est la valeur de Game. Le game thread est le goulot ; le GPU (12 ms) et le render thread (8 ms) attendent. Baisser la résolution ou les ombres ne ferait gagner aucune image par seconde. Objectif : passer le game thread sous 16,7 ms, donc gagner au moins 9 ms.

  1. Confirmer et localiserstat game pour une première répartition (Tick des Actors, des composants…), puis une trace -trace=cpu,frame,bookmark dans Unreal Insights. Sur la piste GameThread d'une frame lente, triez les timers par temps inclusif.
  2. Traiter les gros postesSelon ce que montre la trace : Tick de nombreux ennemis (intervalles, Significance Manager, timers) ; Blueprints coûteux (Get All Actors Of Class, boucles lourdes à passer en C++) ; animation (URO, pas d'animation hors écran, mise à jour multithread : vérifier avec stat anim) ; IA (services et perception moins fréquents) ; physique (moins de corps simulés) ; spawns en rafale (pooling).
  3. Mesurer après chaque changementUn changement à la fois, toujours dans le même passage de jeu, pour savoir ce qui a réellement fait gagner du temps.

Ensuite. Une fois le game thread sous 12 ms, c'est le GPU (12 ms) qui deviendra l'étage le plus lent : le jeu plafonnera vers 80 fps. C'est largement suffisant pour 60 fps ; pour viser 120 fps (8,3 ms), il faudrait alors optimiser aussi le GPU, en commençant par le test de r.ScreenPercentage.

Un testeur rapporte qu'un pointeur vers l'effet de tir est parfois nul. Vous voulez être prévenu avec la pile d'appels, sans faire planter le jeu. Quelle macro utiliser ?

  • check(MuzzleFX)
  • verify(MuzzleFX)
  • if (!ensure(MuzzleFX)) return;
  • checkNoEntry()

ensure écrit une erreur avec la pile d'appels (une fois par emplacement) mais laisse le jeu continuer, et renvoie le résultat du test, ce qui permet de sortir proprement de la fonction. check et verify font planter le programme si la condition est fausse.

À retenir

  • Déboguez votre code en DebugGame Editor avec points d'arrêt, conditions, espions et pile d'appels ; lisez les crashs dans Saved/Crashes et Saved/Logs.
  • check pour l'impossible, ensure pour l'anormal mais récupérable ; logs par catégorie, DrawDebug*, variables console et Visual Logger pour comprendre.
  • On raisonne en millisecondes : 16,7 ms à 60 fps. La frame est imposée par l'étage le plus lent (Game, Draw, RHIT ou GPU) : stat unit le désigne.
  • Unreal Insights dit où passe le temps ; instrumentez votre code avec TRACE_CPUPROFILER_EVENT_SCOPE.
  • CPU : moins de Tick, des événements, du cache, du pooling. GPU : draw calls, pixels (résolution, post-process, translucidité), ombres et Lumen.
  • Mémoire : attention aux références dures et aux casts ; Size Map et Reference Viewer les révèlent. Profilez toujours un build packagé.
