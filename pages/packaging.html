Packaging & publication

Un jeu qui ne tourne que dans l'éditeur n'est pas un jeu : il faut le transformer en exécutable autonome, le tester sur d'autres machines, puis le mettre entre les mains des joueurs. Ce chapitre couvre toute la chaîne, de la configuration de build jusqu'à la page Steam, sans oublier la licence d'Unreal.

Dans ce chapitre

  • Choisir la bonne configuration de build (Development, Shipping…) et la bonne cible
  • Comprendre le cook et pourquoi certains assets disparaissent du jeu packagé
  • Packager depuis l'éditeur, puis en ligne de commande avec BuildCookRun
  • Diagnostiquer les erreurs courantes de packaging
  • Publier sur Steam, l'Epic Games Store ou itch.io
  • Comprendre la licence d'Unreal Engine et ses redevances

Configurations et cibles de build

« Builder », c'est compiler votre code C++ (et celui du moteur) avec l'Unreal Build Tool pour une plateforme, une cible et une configuration données. La configuration règle le compromis entre vitesse d'exécution et outils de débogage :

ConfigurationOptimisationOutils de debugUsage
DebugMoteur et jeu non optimisésTousDéboguer le moteur lui-même (moteur compilé depuis les sources)
DebugGameMoteur optimisé, votre code non optimiséTousDéboguer pas à pas votre code
DevelopmentTout optimiséConsole, logs, stats, checkLa configuration par défaut, celle de l'éditeur et des builds de test internes
TestComme ShippingQuelques outils (console, stats)Mesurer les performances dans des conditions proches du final
ShippingOptimisation maximaleAucunLa version distribuée aux joueurs

La cible (target) indique ce que l'on construit. Chaque cible correspond à un fichier .Target.cs dans le dossier Source :

Editor
MyGameEditor.Target.cs : votre module chargé dans l'éditeur. C'est ce que vous compilez au quotidien (« Development Editor »).
Game
MyGame.Target.cs : le jeu autonome, capable d'être client et serveur (listen server). La cible standard d'un packaging.
Client
Un jeu sans le code serveur, pour les jeux multijoueur à serveurs dédiés.
Server
Un serveur dédié sans affichage. Les cibles Client et Server demandent un moteur compilé depuis les sources (voir Réseau & multijoueur).

Ce que Shipping retire

Une build Shipping est plus rapide et plus difficile à bidouiller, car le moteur y supprime à la compilation tout ce qui sert au développement :

  • la console (touche ²) et les commandes de triche du CheatManager ;
  • les logs : les UE_LOG disparaissent (les réactiver passe par le .Target.cs, ce qui impose en pratique un moteur compilé depuis les sources) ;
  • les commandes stat, le dessin de debug (DrawDebugLine…) et les messages Print String ;
  • les assertions check() et checkf() : leur expression n'est même plus évaluée. Utilisez verify() si l'expression a un effet nécessaire.

Testez en Shipping avant la sortie

Un bug qui n'apparaît qu'en Shipping est presque toujours lié à ce qui a été retiré : un check() qui contenait un appel de fonction, une logique cachée dans un log, ou une variable non initialisée qu'une build Development masquait. Packagez en Shipping régulièrement, pas seulement la veille de la sortie.

Le cook : préparer les assets

Dans l'éditeur, vos assets contiennent des données d'édition et des formats génériques. Le cook les convertit pour une plateforme précise : textures compressées au format du GPU cible (BC sur PC, ASTC sur mobile), shaders compilés pour l'API graphique (DirectX 12, Vulkan, Metal), données d'éditeur supprimées. C'est souvent l'étape la plus longue d'un packaging.

Point crucial : le cook n'emporte que ce qui est référencé. Il part des niveaux à inclure et suit les références de proche en proche ; tout le reste est ignoré, même s'il est dans le dossier Content.

  • List of maps to include in a packaged build (Project Settings → Packaging, section avancée) : listez tous vos niveaux, y compris ceux chargés par OpenLevel. Si la liste est vide, le moteur cuisine tous les niveaux du projet, ce qui gonfle le jeu.
  • Additional Asset Directories to Cook : des dossiers entiers à inclure de force, pour les assets chargés dynamiquement.
  • Primary Asset Labels et règles de l'Asset Manager : la méthode propre pour déclarer des assets chargés à la demande (objets d'inventaire, personnages jouables).

Pak, IoStore, compression et chiffrement

Pak
Plutôt que des milliers de petits fichiers, les assets cookés sont regroupés dans des conteneurs .pak : moins de fichiers, chargement plus rapide, distribution plus simple.
IoStore
Le format de conteneur moderne d'UE5 (option Use Io Store, active par défaut) : des paires .utoc (table des matières) et .ucas (données), accompagnées d'un petit .pak. Optimisé pour le chargement asynchrone rapide.
Compression
Les conteneurs sont compressés (Oodle par défaut en UE5). Un niveau de compression élevé, réservé aux builds de distribution, réduit le téléchargement au prix d'un packaging plus long.
Chiffrement et signature
Dans Project Settings → Crypto, générez une clé pour chiffrer les conteneurs et activez la signature pour détecter les fichiers modifiés. Le chiffrement décourage l'extraction occasionnelle, mais la clé est dans l'exécutable : ce n'est pas une protection absolue.

Packager depuis l'éditeur

  1. Décrire le projetProject Settings → Project → Description : Project Name, Project Version, Company Name, Copyright Notice, Project Displayed Title (le titre de la fenêtre) et la vignette.
  2. Choisir les niveauxProject → Maps & Modes : Game Default Map est le niveau chargé au lancement du jeu (votre menu principal) ; Editor Startup Map n'affecte que l'éditeur. Réglez aussi le Default GameMode.
  3. Régler le packagingProject → Packaging : Build Configuration (Shipping pour la sortie), Use Pak File et Use Io Store (laissez-les cochés), Full Rebuild (repart de zéro, plus lent mais plus sûr), For Distribution (obligatoire pour les stores mobiles et consoles), la liste des niveaux à inclure et, dans les options avancées, Include prerequisites installer.
  4. Plateformes et identité visuelleProject → Supported Platforms : cochez les plateformes visées. Platforms → Windows : l'icône du jeu (Game Icon, un fichier .ico de 256 × 256) et l'image de démarrage (Game Splash), ainsi que les API graphiques ciblées (Targeted RHIs).
  5. Lancer le packagingDans la barre d'outils, menu Platforms → Windows : choisissez la Binary Configuration (Shipping), puis Package Project et un dossier de sortie. Suivez la progression dans l'Output Log : le packaging se termine par BUILD SUCCESSFUL ou par l'erreur à corriger.

Où sont les sauvegardes et les logs ?

Un jeu packagé sous Windows écrit ses données dans %LOCALAPPDATA%\MyGame\Saved\ : SaveGames, Logs, Config (dont GameUserSettings.ini) et Crashes. Le dossier d'installation reste en lecture seule, ce qui est indispensable sous Program Files.

Packager en ligne de commande

Pour automatiser les builds (script, serveur d'intégration continue, build nocturne), on appelle directement UAT. C'est exactement ce que fait l'éditeur, en reproductible :

ArgumentRôle
-projectChemin complet du .uproject
-platform=Win64Plateforme cible (Linux, Android, Mac, IOS…)
-clientconfig=ShippingConfiguration du jeu (-serverconfig pour un serveur dédié)
-build, -cook, -stageLes étapes à exécuter : compiler, cooker, rassembler
-pak, -iostoreProduire les conteneurs

Sous Linux et macOS, le script s'appelle RunUAT.sh. L'éditeur propose aussi le Project Launcher (menu Tools ou Platforms selon votre version) : vous y créez des profils personnalisés (configuration, niveaux à cooker, cook incrémental, déploiement direct sur un appareil Android branché…) réutilisables en un clic.

SymptômeCause probableSolution
Écran noir ou mauvais niveau au lancementGame Default Map non réglé, ou niveau absent de la liste à cookerRégler Maps & Modes, ajouter tous les niveaux à List of maps to include
Objet, son ou texture manquant en jeu, mais présent dans l'éditeurAsset chargé par un chemin écrit dans une chaîne : le cooker ne l'a pas vuUtiliser une référence (TSoftObjectPtr, propriété), un Primary Asset Label ou Additional Asset Directories to Cook

Le dernier cas mérite un exemple, car il surprend tous les débutants : le jeu compile parfaitement dans l'éditeur, puis le packaging échoue.

Votre jeu packagé lance bien le menu, mais un objet d'inventaire chargé avec LoadObject(nullptr, TEXT("/Game/Items/Epee.Epee")) renvoie nullptr. Pourquoi ?

  • LoadObject ne fonctionne pas en Shipping
  • Rien ne référence l'asset : le cooker ne l'a pas inclus
  • Il fallait packager en Development
  • Les chemins doivent être en minuscules

Le cooker suit les références, pas les chaînes de caractères. Référencez l'asset via une propriété (TSoftObjectPtr, Data Asset…), un Primary Asset Label, ou ajoutez son dossier à Additional Asset Directories to Cook.

Tester ses builds

  • Lancez avec des arguments : -log ouvre une fenêtre de log (en Development), -windowed -ResX=1280 -ResY=720 force une fenêtre.
  • Testez sur d'autres machines : une configuration modeste, un portable, une machine « propre » sans Visual Studio ni Unreal (elle révèle les prérequis manquants), un Steam Deck si vous le visez.
  • Vérifiez les réglages par défaut : au premier lancement, quelle qualité graphique est choisie ? Le jeu reste-t-il jouable sur la machine la plus faible ? (Voir la scalabilité dans Matériaux, lumière & VFX.)
  • Préparez les crashs : cochez Include Crash Reporter dans les réglages de packaging et archivez les symboles (.pdb) de chaque version distribuée, sans les livrer aux joueurs. Sans eux, une pile d'appels de crash est illisible.

Les plateformes

Windows

La cible naturelle

Packaging direct depuis l'éditeur, DirectX 12 par défaut (DirectX 11 et Vulkan possibles). La plateforme de développement de référence.

Linux

Compilation croisée

Depuis Windows, installez la toolchain clang fournie par Epic pour votre version du moteur (variable d'environnement LINUX_MULTIARCH_ROOT). Linux apparaît alors dans Platforms.

macOS / iOS

Un Mac est obligatoire

La compilation et la signature passent par Xcode sur un Mac, et un compte Apple Developer est nécessaire pour distribuer.

Android

SDK et NDK

Installez Android Studio, puis les versions de SDK, NDK et JDK exigées par votre version du moteur (script SetupAndroid dans Engine/Extras/Android). Sortie en APK ou AAB pour le Play Store.

Consoles

Accès sous NDA

PlayStation, Xbox et Switch exigent d'être accepté comme développeur par le constructeur, un accord de confidentialité et des kits de développement. Les outils Unreal correspondants sont fournis après validation.

Publier son jeu

Steam

  1. Compte SteamworksInscrivez-vous comme partenaire Steamworks (informations fiscales et bancaires), puis payez les frais Steam Direct : 100 USD par jeu, récupérés une fois que le jeu a généré 1 000 USD de revenus bruts.
  2. App ID et depotsSteam crée un App ID (l'identifiant du jeu) et des depots (des lots de fichiers, par exemple un par système d'exploitation). Les branches permettent de publier une bêta à côté de la version stable.
  3. Page du magasinCaptures, bande-annonce, description, configuration requise. La page doit être publiée en « Coming Soon » un certain temps avant la sortie, et passe, comme la build, par une revue de Valve : consultez les délais actuels dans la documentation Steamworks.
  4. Envoyer la buildAvec SteamPipe : le dossier tools/ContentBuilder du SDK Steamworks contient steamcmd et des scripts .vdf qui décrivent quoi envoyer dans quel depot.
  5. PublierDans Steamworks, rendez la build active (Set build live) sur la branche default : les joueurs la téléchargent.

Copiez au préalable le contenu de votre dossier Windows/ packagé dans ContentBuilder/content/. Pour les succès, le classement et l'overlay Steam, activez le plugin Online Subsystem Steam et configurez-le ; les nœuds d'Online Subsystem (Cache Achievements, Write Achievement Progress) gèrent ensuite les succès déclarés dans Steamworks.

Pensez au Steam Deck : Valve évalue les jeux (Verified, Playable, Unsupported). Une build Windows y tourne via la couche de compatibilité Proton ; les critères principaux sont une prise en charge complète de la manette, un texte lisible en 1280 × 800 et l'absence de lanceur externe problématique.

Epic Games Store et itch.io

L'Epic Games Store est ouvert à l'auto-publication via le portail développeur d'Epic. Le partage de revenus standard est de 88 % pour le développeur et 12 % pour Epic, et Epic a annoncé des conditions encore plus favorables sur une partie des premiers revenus : vérifiez les conditions en vigueur. Les services en ligne Epic Online Services (succès, amis, multijoueur multiplateforme) sont gratuits et utilisables même hors de l'EGS.

itch.io est la porte d'entrée la plus simple : aucun frais, publication en quelques minutes, et vous choisissez vous-même la part reversée à la plateforme (10 % par défaut). Idéal pour une game jam, une démo ou un premier jeu. L'outil en ligne de commande butler envoie et met à jour les builds en ne transférant que les différences :

Pour les mises à jour, les magasins comme Steam ne téléchargent que les blocs modifiés des fichiers. Unreal peut aussi produire de vrais paks de patch qui ne contiennent que le contenu modifié : on crée une version de référence au lancement (argument -createreleaseversion=1.0), puis on génère un patch par rapport à elle (-generatepatch -basedonreleaseversion=1.0). Pour télécharger du contenu depuis votre propre serveur (DLC, jeux mobiles), le plugin ChunkDownloader récupère des paks à la demande.

La licence Unreal Engine

Unreal Engine est gratuit à télécharger et à utiliser, code source compris. Pour un jeu commercialisé, le principe de l'EULA (le contrat de licence) est le suivant :

  • une redevance de 5 % du chiffre d'affaires brut d'un produit, seulement au-delà du premier million de dollars de revenus cumulés sur toute la vie de ce produit ;
  • les revenus réalisés via l'Epic Games Store sont exonérés ;
  • des déclarations trimestrielles de revenus sont à transmettre à Epic une fois les seuils concernés atteints, et Epic demande d'être prévenu de la sortie du jeu ;
  • Epic propose parfois des taux réduits via des programmes spécifiques, par exemple pour les jeux qui sortent aussi sur l'Epic Games Store.

Exemple : un jeu vendu uniquement sur Steam génère 1 500 000 USD de revenus bruts au total. La redevance porte sur 1 500 000 − 1 000 000 = 500 000 USD, soit 5 % × 500 000 = 25 000 USD. Attention, « brut » signifie avant la commission du magasin : la base de calcul n'est pas ce que Steam vous verse.

Vérifiez la version actuelle de l'EULA

Les conditions de licence évoluent (seuils, exonérations, programmes à taux réduit, règles pour les usages hors jeu vidéo). Ce résumé n'est pas un conseil juridique : avant de commercialiser votre jeu, lisez la version actuelle de l'EULA d'Unreal Engine sur le site d'Epic et sa FAQ, et respectez aussi la mention de copyright et les règles d'utilisation des marques et logos.

Votre jeu, vendu sur Steam et sur l'Epic Games Store, a rapporté 800 000 USD bruts sur Steam et 300 000 USD sur l'EGS. Que devez-vous à Epic au titre de la licence Unreal ?

  • 5 % de 1 100 000 USD
  • 5 % de 100 000 USD
  • Rien : les revenus soumis à redevance (hors EGS) n'ont pas dépassé le million de dollars
  • 12 % des ventes EGS

Les ventes sur l'Epic Games Store sont exonérées de redevance, et le million de dollars des autres revenus n'est pas atteint. Les 12 % sont la commission du magasin EGS, pas la redevance du moteur. Vérifiez toujours ces règles dans l'EULA en vigueur.

Une build Shipping avec icône et niveau de démarrage

Packagez votre projet (par exemple celui du projet guidé) en Shipping pour Windows. Le jeu doit démarrer sur le menu principal, afficher votre propre icône dans l'explorateur Windows et la barre des tâches, et fonctionner sur une autre machine.

Voir la solution
  1. Préparer l'icôneCréez une image carrée et convertissez-la en .ico contenant une taille de 256 × 256 (la plupart des outils d'image le font).
  2. Régler l'identitéProject Settings → Description : nom, version 1.0.0, entreprise. Platforms → Windows → Game Icon : choisissez votre .ico.
  3. Régler les niveauxMaps & Modes → Game Default Map = votre menu principal. Packaging → List of maps to include : ajoutez le menu et tous les niveaux de jeu.
  4. Régler le packagingPackaging → Build Configuration = Shipping, Full Rebuild et For Distribution cochés, Include prerequisites installer coché.
  5. PackagerPlatforms → Windows → Binary Configuration = Shipping, puis Package Project. Attendez BUILD SUCCESSFUL dans l'Output Log.
  6. VérifierDans le dossier Windows/, MyGame.exe affiche votre icône. Copiez tout le dossier sur une autre machine (lancez d'abord UEPrereqSetup_x64.exe depuis Engine/Extras/Redist si besoin) et vérifiez que le menu apparaît, que les niveaux se chargent et qu'aucun asset ne manque.

Si l'icône n'a pas changé : elle est intégrée à l'exécutable, faites un Full Rebuild. Si le problème persiste sur un projet uniquement Blueprint, ajouter une classe C++ (même vide) force la compilation d'un exécutable propre au projet. Enfin, l'explorateur Windows garde parfois l'ancienne icône en cache.

À retenir

  • Development pour travailler, Shipping pour distribuer : Shipping retire console, logs, stats et check().
  • Le cook n'inclut que ce qui est référencé : déclarez vos niveaux et vos assets chargés dynamiquement.
  • Le packaging enchaîne Build, Cook, Stage, Package, Archive ; RunUAT BuildCookRun fait de même en ligne de commande.
  • Protégez le code d'éditeur avec WITH_EDITOR, incluez les prérequis et testez sur une machine vierge.
  • Steam : 100 USD par jeu, SteamPipe pour envoyer les builds ; EGS : 88/12 et revenus exonérés de redevance ; itch.io : le plus simple.
  • Licence Unreal : 5 % au-delà du premier million de revenus bruts par produit, hors EGS. Vérifiez toujours l'EULA en vigueur.
