Blueprints : le scripting visuel

Les Blueprints permettent de programmer un jeu entier en reliant des nœuds, sans écrire une ligne de code. Ce n'est pas un jouet : c'est un vrai langage, compilé, orienté objet, avec variables, fonctions, héritage et interfaces. Ce chapitre vous apprend à lire et écrire un graphe, à structurer votre logique, et surtout à faire communiquer vos Blueprints entre eux, la question qui bloque tous les débutants.

Dans ce chapitre

  • Comprendre ce qu'est un Blueprint et en connaître les différents types
  • Lire un graphe : nœuds, pins d'exécution et pins de données, couleurs des types
  • Utiliser variables, fonctions, macros et Custom Events
  • Contrôler le flux : Branch, Sequence, boucles, Delay, timers
  • Générer du contenu avec le Construction Script
  • Faire communiquer les Blueprints : référence directe, cast, interface, Event Dispatcher
  • Déboguer un Blueprint et l'articuler avec du C++

Qu'est-ce qu'un Blueprint ?

Un Blueprint Class (souvent simplement « Blueprint ») est une classe, exactement comme une classe C++ : un plan à partir duquel on crée des objets. Quand vous créez BP_Orb à partir de la classe Actor, vous créez une classe enfant d'AActor. Chaque orbe posée dans le niveau est une instance de cette classe, avec ses propres valeurs de variables.

Il existe plusieurs sortes d'assets Blueprint, chacune avec un rôle précis :

TypePréfixeRôle
Blueprint ClassBP_Une classe : Actor, Pawn, Character, Component, GameMode… Le cas le plus courant.
Level Blueprint—Un graphe unique attaché à un niveau. Pratique pour un événement scripté, mais non réutilisable : à utiliser avec parcimonie.
Blueprint InterfaceBPI_Une liste de fonctions sans implémentation, que plusieurs classes peuvent implémenter.
Blueprint Function LibraryBPFL_Des fonctions statiques utilisables depuis n'importe quel Blueprint.
Blueprint Macro LibraryBPML_Des macros partagées entre Blueprints d'une même classe de base.
Widget BlueprintWBP_Une interface utilisateur UMG (voir Interfaces avec UMG).
Animation BlueprintABP_La logique d'animation d'un Skeletal Mesh (voir Animation).

Les Blueprints sont compilés

Le bouton Compile transforme votre graphe en bytecode exécuté par une machine virtuelle du moteur. Un Blueprint est donc plus lent que du C++ natif (surtout dans les boucles lourdes), mais largement assez rapide pour la logique de gameplay courante. Le vrai coût se cache rarement dans « Blueprint contre C++ » : il vient bien plus souvent d'un Tick inutile ou d'une boucle sur des milliers d'éléments.

L'éditeur de Blueprint

Double-cliquez sur un Blueprint Class : son éditeur s'ouvre. On y retrouve toujours les mêmes zones :

Components
En haut à gauche : la hiérarchie des composants de l'Actor (mesh, collision, caméra, son…). Le bouton + Add en ajoute. Le premier composant est la racine (DefaultSceneRoot par défaut).
My Blueprint
En bas à gauche : les graphes, fonctions, macros, variables et Event Dispatchers de la classe. C'est ici qu'on les crée, avec les boutons +.
Viewport
L'aperçu 3D de l'Actor et de ses composants.
Event Graph
Le graphe principal, où l'on réagit aux événements (BeginPlay, overlap, input…).
Construction Script
Un graphe spécial exécuté dans l'éditeur à chaque modification de l'Actor (voir plus bas).
Details
À droite : les propriétés de ce qui est sélectionné (composant, variable, nœud).
Class Defaults / Class Settings
Boutons de la barre d'outils : les valeurs par défaut de la classe, et ses réglages (classe parente, interfaces implémentées).

Ajouter un nœud

Clic droit dans le graphe ouvre la palette contextuelle : tapez le nom du nœud (« print », « delay », « get actor location »). L'option Context Sensitive filtre les nœuds compatibles. Encore plus rapide : tirez un fil depuis un pin et relâchez dans le vide, la palette ne propose alors que des nœuds acceptant ce type.

Lire un graphe : nœuds et pins

Un graphe Blueprint contient deux sortes de fils, et toute la lecture repose sur cette distinction :

Les fils d'exécution (blancs)

Ils relient les pins en forme de flèche ▷. Ils disent dans quel ordre les actions se produisent. L'exécution part d'un événement (nœud rouge) et suit le fil blanc de gauche à droite.

Les fils de données (colorés)

Ils relient les pins ronds. Ils transportent des valeurs : un nombre, un texte, un objet. Leur couleur indique le type. Une valeur est calculée au moment où un nœud exécuté en a besoin.

Les variables

Dans le panneau My Blueprint, le bouton + Variable crée une variable. Choisissez son type dans Details, compilez, puis donnez-lui une valeur par défaut. Glissez-la dans le graphe : Ctrl + glisser crée un nœud Get (lire), Alt + glisser un nœud Set (écrire).

Instance Editable (l'œil)
La variable apparaît dans le panneau Details de chaque instance placée dans le niveau : un level designer peut régler chaque orbe différemment.
Expose on Spawn
La variable devient un paramètre du nœud Spawn Actor from Class : on fixe sa valeur au moment de la création.
Private
Les autres Blueprints ne peuvent pas la lire ni l'écrire : on passe par des fonctions.
Category
Regroupe les variables dans Details et dans My Blueprint.
Tooltip
Le texte affiché au survol. Documentez vos variables : c'est la seule doc que lira votre game designer.
Replication
Synchronise la variable en multijoueur (voir Réseau & multijoueur).

Les nœuds purs sont recalculés à chaque lecture

Un nœud vert (pur) n'a pas de pin d'exécution : il est réévalué chaque fois qu'un nœud exécuté lit sa sortie. Si vous branchez la sortie de Random Integer sur deux nœuds, vous obtiendrez deux nombres différents. Si un calcul pur est coûteux (Get All Actors Of Class, une recherche dans un tableau) ou aléatoire, stockez son résultat dans une variable locale avant de l'utiliser plusieurs fois.

Tableaux, maps et sets

Toute variable peut devenir un conteneur grâce à l'icône à droite de son type : Array (liste ordonnée, accès par index), Set (ensemble sans doublons) ou Map (dictionnaire clé → valeur). Ce sont les équivalents de TArray, TSet et TMap en C++. Les nœuds utiles : Add, Remove, Get (a copy), Length, Contains, Find, et la boucle For Each Loop.

Fonctions, macros et Custom Events

Un Event Graph de 300 nœuds devient vite illisible (« spaghetti »). Trois outils permettent de découper la logique :

FonctionMacroCustom Event
Valeur de retourOui (plusieurs sorties possibles)OuiNon
Variables localesOuiNon (seulement des nœuds Local Variable de macro)Non
Nœuds latents (Delay, Timeline)NonOuiOui
Plusieurs sorties d'exécutionNonOui (comme Branch)Non
Appelable depuis un autre BlueprintOuiNonOui
Peut être lié à un timer ou un dispatcherOui (par nom, avec Set Timer by Function Name)NonOui
Réplication réseau (RPC)NonNonOui

Règle simple : par défaut, une fonction. Un Custom Event quand vous avez besoin d'un Delay, d'un timer, d'un dispatcher ou d'un RPC. Une macro quand vous voulez plusieurs sorties d'exécution, ce qui reste rare.

Cochez Pure dans les détails d'une fonction qui ne modifie rien (un calcul, un getter) : elle perd ses pins d'exécution et devient verte. Cochez Const si elle ne modifie pas l'objet. Sélectionnez un groupe de nœuds puis clic droit → Collapse to Function pour transformer un morceau de graphe existant en fonction.

Contrôler le flux d'exécution

Les nœuds gris de contrôle de flux sont les « mots-clés » du langage :

Branch
Le if : suit True ou False selon une condition.
Sequence
Exécute Then 0, puis Then 1, puis Then 2… Utile pour aérer un graphe. Attention : si une branche contient un Delay, la suivante n'attend pas.
Switch on Int / Enum / String
Le switch : une sortie par valeur.
For Loop / For Each Loop / While Loop
Les boucles. Elles s'exécutent entièrement dans la même frame : une boucle de 100 000 tours fige le jeu, et une boucle infinie déclenche l'erreur « Infinite loop detected ».
Do Once / Do N
Ne laisse passer l'exécution qu'une fois (ou N fois) jusqu'à Reset.
Flip Flop
Alterne entre la sortie A et la sortie B à chaque passage : idéal pour un interrupteur.
Gate
Une porte qu'on ouvre (Open) et ferme (Close) : l'exécution ne passe que si elle est ouverte.
Delay
Un nœud latent : il reprend l'exécution après une durée, sans bloquer le jeu. Rappeler un Delay déjà en cours est ignoré.
Is Valid
Vérifie qu'une référence d'objet n'est ni vide ni en cours de destruction. À utiliser avant d'accéder à un objet qui a pu disparaître.

Les timers

Pour répéter une action à intervalle régulier (un chrono, une régénération), n'utilisez ni le Tick ni une boucle de Delay : utilisez un timer. Set Timer by Event appelle un Custom Event après un délai, éventuellement en boucle, et renvoie un Timer Handle qui permet de le mettre en pause ou de l'arrêter (Clear and Invalidate Timer by Handle).

Event Tick : à manier avec précaution

Event Tick s'exécute à chaque frame, avec le Delta Seconds écoulé depuis la frame précédente. C'est le bon outil pour un mouvement continu ou une interpolation de caméra ; c'est le mauvais outil pour vérifier « est-ce que la partie est finie ? » soixante fois par seconde. Préférez les événements (overlap, dégâts, dispatcher) et les timers. Si une classe n'a pas besoin du Tick, décochez Start with Tick Enabled dans Class Defaults.

Vous branchez la sortie d'un nœud Random Integer in Range (1, 6) à la fois sur un Print String et sur une variable SET LastRoll. Le texte affiché et la valeur stockée diffèrent. Pourquoi ?

  • Le Print String arrondit les entiers
  • Un nœud pur est réévalué à chaque lecture : chaque nœud qui lit la sortie obtient un nouveau tirage
  • Il faut compiler le Blueprint deux fois
  • SET ne fonctionne pas avec des valeurs aléatoires

Les nœuds purs n'ont pas de mémoire. Pour garder un tirage, enregistrez-le d'abord dans une variable (SET), puis lisez cette variable partout où vous en avez besoin.

Le Construction Script

Le Construction Script s'exécute dans l'éditeur, chaque fois que l'Actor est placé, déplacé ou qu'une de ses propriétés change, et une fois de plus quand il apparaît en jeu. Il sert à construire l'Actor en fonction de ses paramètres : une clôture dont on règle le nombre de poteaux, une lampe dont on choisit la couleur, une rangée d'orbes.

Rien de lourd dans le Construction Script

Il est réexécuté à chaque déplacement de la souris quand vous faites glisser l'Actor : un traitement coûteux rend l'éditeur saccadé. N'y faites pas non plus de logique de jeu (dégâts, score, sons) : elle appartient à BeginPlay. Pour beaucoup de copies d'un même mesh, préférez un Instanced Static Mesh Component et Add Instance, bien moins coûteux qu'un composant par copie.

Faire communiquer les Blueprints

Votre personnage ramasse une orbe : l'orbe doit prévenir le score. Le joueur appuie sur un bouton : la porte doit s'ouvrir. Faire parler deux Blueprints est la compétence clé. Il existe quatre techniques, chacune adaptée à une situation :

1. La référence directe

Le cas le plus simple : un bouton doit ouvrir cette porte. Dans BP_Button, créez une variable TargetDoor de type BP_Door (Object Reference), cochez Instance Editable, compilez. Dans le niveau, sélectionnez le bouton et choisissez la porte dans le champ TargetDoor avec la pipette. Le bouton peut alors appeler directement les fonctions de la porte.

2. Le cast

Beaucoup d'événements vous donnent une référence générique : Event ActorBeginOverlap fournit un Actor, Get Player Character un Character. Pour accéder aux variables et fonctions propres à votre classe, il faut convertir cette référence : c'est le Cast. Si l'objet est bien du type demandé (ou d'une classe enfant), la sortie principale est suivie avec la référence convertie ; sinon, c'est Cast Failed.

Le vrai coût du cast : les dépendances

Un cast en lui-même est très rapide. Mais un nœud Cast To BP_Boss crée une référence dure : charger votre Blueprint charge aussi BP_Boss, ses meshes, ses textures, ses sons… Multipliez les casts vers des Blueprints lourds et chaque asset finit par tout charger en mémoire. Castez de préférence vers des classes C++ ou des Blueprints parents légers, et utilisez des interfaces quand plusieurs types sont possibles. Le Size Map révèle ces chaînes de dépendances.

3. Les Blueprint Interfaces

Le joueur appuie sur « Interagir » devant un objet. Ce peut être une porte, un coffre, un levier, un PNJ… Faire un cast vers chacun serait interminable. Une interface définit un contrat : « je sais répondre à Interact ». Chaque classe qui l'implémente fournit sa propre réponse, et l'appelant n'a pas besoin de connaître le type exact.

  1. Créer l'interfaceClic droit → Blueprints → Blueprint Interface : BPI_Interactable. Ajoutez une fonction Interact avec une entrée Instigator (Pawn). Pas d'implémentation ici : seulement la signature.
  2. L'implémenterDans BP_Door, Class Settings → Implemented Interfaces → Add → BPI_Interactable. L'événement Event Interact apparaît dans My Blueprint : implémentez-le.
  3. Envoyer le messageDans le personnage, appelez Interact (Message) sur l'Actor visé. Si l'Actor n'implémente pas l'interface, rien ne se passe, sans erreur ni cast.

Message ou appel direct ?

Sur une référence de type quelconque, la palette propose Interact (Message) : il fonctionne sur n'importe quel objet et ne fait rien si l'interface n'est pas implémentée. Pour savoir à l'avance si un objet répond, utilisez Does Implement Interface. En C++, une interface se déclare avec UINTERFACE et s'appelle avec IInteractable::Execute_Interact(Actor, Instigator) ; voir C++ avancé.

4. Les Event Dispatchers

Les trois techniques précédentes vont de l'émetteur vers un receveur qu'il connaît. Parfois c'est l'inverse : un objet veut annoncer qu'il s'est passé quelque chose, sans savoir qui est intéressé. Le boss meurt : la musique doit changer, une porte doit s'ouvrir, le HUD doit afficher « Victoire ». Le boss ne devrait connaître aucun de ces objets. C'est le rôle de l'Event Dispatcher (le délégué multicast du C++) : l'émetteur l'appelle (Call), les intéressés s'y abonnent (Bind).

Un levier doit pouvoir activer, selon le niveau, une porte, une plateforme mobile ou un piège. Quelle technique est la plus adaptée pour que le levier appelle l'objet qu'on lui a assigné ?

  • Trois casts successifs vers BP_Door, BP_Platform et BP_Trap
  • Une interface BPI_Activatable implémentée par les trois classes, et une variable Actor Instance Editable dans le levier
  • Un Level Blueprint par niveau
  • Get All Actors Of Class à chaque activation

Le levier ne connaît que l'interface : on peut ajouter demain un quatrième type activable sans toucher au levier. Les casts en cascade créent trois références dures et doivent être modifiés pour chaque nouveau type.

Déboguer un Blueprint

  • Print String : le réflexe de base. Il affiche un message à l'écran et dans l'Output Log. Donnez une Key pour remplacer le message précédent au lieu de les empiler.
  • Points d'arrêt : sélectionnez un nœud et appuyez sur F9. Le jeu se fige quand l'exécution l'atteint ; F10 avance d'un nœud, F11 entre dans une fonction.
  • Watch Value : clic droit sur un pin → Watch this value affiche sa valeur pendant l'exécution, et survoler un pin au point d'arrêt montre sa valeur actuelle.
  • Choisir l'instance déboguée : pendant le PIE, le menu Debug Object de la barre d'outils choisit quelle instance observer. Les fils parcourus s'illuminent en temps réel.
  • Blueprint Debugger : Tools → Debug → Blueprint Debugger affiche la pile d'appels et les variables surveillées.
  • Erreurs de compilation : le panneau Compiler Results liste les problèmes ; cliquer sur une erreur sélectionne le nœud fautif. Un nœud marqué « ERROR » ou un pin non connecté obligatoire empêche la compilation.

« Accessed None trying to read property »

L'erreur Blueprint la plus fréquente : vous utilisez une variable de référence qui est vide (None). Soit elle n'a jamais été assignée (oubli dans Details, cast raté), soit l'objet a été détruit. Le message d'erreur à la fin du PIE indique le Blueprint, la fonction et le nœud : cliquez dessus. La solution : assigner la référence, ou la protéger avec Is Valid.

Quand passer au C++ ?

Restez en Blueprint tant que vous êtes productif. Envisagez le C++ quand un graphe devient trop complexe pour être lu, quand une boucle traite des centaines d'éléments par frame, quand vous avez besoin d'une API non exposée aux Blueprints, ou quand plusieurs personnes doivent modifier la même logique (les Blueprints sont des fichiers binaires qui ne se fusionnent pas).

Vous voulez qu'un Delay de 2 secondes s'exécute au milieu d'un traitement réutilisable appelé depuis plusieurs endroits du graphe. Que créez-vous ?

  • Une fonction : c'est toujours le meilleur choix
  • Un Custom Event (ou une macro), car les fonctions ne peuvent pas contenir de nœud latent comme Delay
  • Une fonction pure
  • Une Blueprint Function Library

Une fonction s'exécute d'un seul tenant et doit se terminer dans la même frame : les nœuds latents (Delay, Timeline, Move To…) y sont interdits. Un Custom Event peut attendre, et il peut aussi être appelé depuis un autre Blueprint.

Un bouton, une porte, un interrupteur

Créez BP_Door (un mesh qui pivote de 90° en une seconde quand il s'ouvre) et BP_PressurePlate (une plaque qui annonce OnActivated quand le joueur monte dessus et OnDeactivated quand il en descend). Une porte doit pouvoir écouter plusieurs plaques et ne s'ouvrir que lorsque toutes sont pressées.

Voir la solution
  1. BP_PressurePlate : un Static Mesh et une Box Collision. Deux Event Dispatchers, OnActivated et OnDeactivated. Sur On Component Begin Overlap de la box, castez l'Actor vers votre personnage (seul le joueur active la plaque) puis Call OnActivated ; sur End Overlap, Call OnDeactivated.
  2. BP_Door : une variable Plates de type tableau de BP_PressurePlate, Instance Editable, et un entier PressedCount. Une Timeline DoorTimeline avec une piste float de 0 à 1 en 1 seconde ; sa sortie Update appelle Set Relative Rotation sur le mesh avec un Yaw de Lerp(0, 90, Alpha).
  3. Au BeginPlay de la porte : For Each Loop sur Plates, et pour chaque plaque Bind Event to OnActivated (Custom Event PlatePressed) et Bind Event to OnDeactivated (Custom Event PlateReleased).
  4. PlatePressed : PressedCount + 1, puis si PressedCount == Length(Plates), Play sur la Timeline. PlateReleased : PressedCount - 1, puis Reverse.
  5. Dans le niveau, sélectionnez la porte et ajoutez les plaques au tableau Plates avec la pipette.

Les plaques ne connaissent pas la porte : vous pouvez réutiliser les mêmes plaques pour déclencher un piège, de la musique ou un ascenseur en ajoutant simplement d'autres écouteurs.

À retenir

  • Un Blueprint Class est une vraie classe qui hérite d'une classe C++ ; les objets du niveau en sont des instances.
  • Fils blancs = ordre d'exécution ; fils colorés = données, dont la couleur indique le type.
  • Les nœuds purs (verts) sont recalculés à chaque lecture : stockez les résultats coûteux ou aléatoires.
  • Par défaut une fonction ; un Custom Event pour les Delay, timers, dispatchers et RPC ; une macro pour plusieurs sorties d'exécution.
  • Le Construction Script construit l'Actor dans l'éditeur ; la logique de jeu va dans BeginPlay et les événements.
  • Communication : référence directe (lien fixe), cast (type connu, attention aux références dures), interface (types variés), Event Dispatcher (annonce à des écouteurs inconnus).
  • Déboguez avec Print String, F9 et Watch Value ; « Accessed None » signale une référence vide.
  • Le C++ expose ses classes avec BlueprintCallable, BlueprintPure, BlueprintImplementableEvent, BlueprintNativeEvent et BlueprintAssignable.
